# Architecture Contract

This document defines the current backend shape. It is normative: new code should fit these boundaries unless the contract is updated in the same change.

## Runtime Surfaces
- REST API: [`app/api/api_v1/api.py`](../app/api/api_v1/api.py) wires all versioned routers; [`app/factory.py`](../app/factory.py) is the composition root; `app/infrastructure/` owns middleware, exception handlers, lifespan, route mounting, and MCP HTTP app construction.
- `app/modules/` is reserved for future physical domain entrypoints. The previous wildcard re-export wrappers have been removed; do not recreate shim-only domain packages.
- Core marketplace and booking flows currently live in the REST endpoint modules under `app/api/api_v1/endpoints/` and shared business logic under `app/services/`.
- Property Management flows are exposed through the `app/api/api_v1/endpoints/pm_*.py` endpoints and the matching `app/services/pm_*.py` modules.
- Tours and media flows are exposed through the tour/storage endpoint and service modules.
- MCP surfaces live in `app/mcp/user/`, `app/mcp/admin/`, and multi-client tool modules such as [`app/mcp/chatgpt/visit_tools.py`](../app/mcp/chatgpt/visit_tools.py). The MCP servers use `AppsSDKFastMCP` with Streamable HTTP transport and support MCP-compatible clients. Widget resources are registered under both stable `ui://widget/*.html` URIs used in tool metadata and content-hashed `?v=<hash>` aliases used for cache-busted result hints. Mounted MCP HTTP apps must expose FastMCP/Starlette lifespan contexts; `app/infrastructure/lifespan.py` enters those contexts during parent app startup.
- AI-agent orchestration lives in `app/services/ai_agent/`, especially [`app/services/ai_agent/tools/`](../app/services/ai_agent/tools/) and `agent_service.py`.
- Vector search and sync live in `app/vector/` and the vector sync scheduler.
- Data Hub aggregation flows live in `app/services/data_hub/`, exposed via `app/api/api_v1/endpoints/data_hub/` and scheduled via `app/services/data_hub_scheduler.py`. RERA, zoning, and colony-approval provenance is persisted by `app/services/data_hub/provenance.py`; source documents store metadata and hashes, not source bodies, and assertion/revision rows enforce exactly one typed entity FK.
- Startup jobs and schedulers are registered from `app/infrastructure/lifespan.py` and currently include blog auto publish, notifications, vector sync, and data hub scraping.

## Layer Contracts
- `app/modules` is a reserved namespace for future domain packages. New code should use the existing concrete homes (`app/api`, `app/services`, `app/models`, `app/schemas`, `app/repositories`, `app/mcp`) until a domain is physically migrated.
- `app/api` remains the REST transport layer and should delegate to module or service entrypoints. It should not own business rules that are needed elsewhere.
- `app/services` remains the legacy business-logic implementation layer during migration and depends on `app.models`, `app.schemas`, `app.repositories`, `app.core`, and narrowly-scoped external clients.
- `app/infrastructure` owns composition and adapters: app factory helpers, database/session lifecycle re-exports, cache, logging context, middleware registration, routes, and lifespan jobs.
- `app/shared` is a reserved namespace for future cross-domain contracts. Current canonical homes remain `app.core.exceptions`, `app.api.api_v1.dependencies.auth`, `app.schemas.common`, `app.core.utils`, and `app.utils`.
- `app/mcp` may depend on module/service entrypoints, schemas, shared errors, and serializer/formatter helpers. MCP tools should not create alternate business-rule paths when a service already exists.
- `app/services/ai_agent` may orchestrate models, tool registration, and streaming, but tool execution should prefer shared service-layer behavior over agent-only mutations.
- `app/models` and `app/schemas` are leaf data layers. They should not import endpoint or transport code.

## Shared HTTP Clients
- `app/core/http.py` owns the shared `httpx.AsyncClient` singletons: `get_scraper_client`, `get_blog_client`, `get_general_client`, `get_supabase_auth_http_client`. New outbound HTTP call sites MUST use these shared clients instead of creating ephemeral `async with httpx.AsyncClient()` blocks.
- The Supabase auth client (`get_supabase_auth_http_client`) is tuned for short, latency-sensitive GoTrue calls (10 s default timeout, 10 max connections, 5 keep-alive) and is used by `app/core/auth.py` for `verify_token` and admin user ops. It is closed via `close_all_clients()` in `app/infrastructure/lifespan.py`.
- Auth verification distinguishes transient provider failures from bad tokens: `app/core/auth.py` returns tagged `AuthFailureReason` results, and `app/api/api_v1/dependencies/auth.py` maps `PROVIDER_UNREACHABLE` to HTTP 503 with `Retry-After: 5` instead of 401. This lets clients distinguish a Supabase outage from an invalid JWT.

## Approved Extension Points
- Add new REST functionality by wiring the REST transport in `app/api/api_v1/endpoints/`, service logic in `app/services/`, and matching schemas in `app/schemas/`. Only add `app/modules/<domain>/` code when the domain implementation is physically migrated there, not as a re-export shim.
- Add new MCP capabilities by extending `app/mcp/user/server.py`, `app/mcp/admin/`, or the multi-client tool modules in `app/mcp/chatgpt/`, while reusing existing services for authz and persistence. Tools must use `AppsSDKToolResult` and include standard annotations (`readOnlyHint`, `openWorldHint`, `destructiveHint`, `securitySchemes`).
- Add new AI-agent capabilities by extending `app/services/ai_agent/tools/` or related agent orchestration files, while keeping transport-specific logic out of shared services.
- Add new background automation via dedicated scheduler modules in `app/services/` and explicit startup wiring in `app/infrastructure/lifespan.py`.
- Keep data-hub provenance private: do not add assertion/history routes in this slice. Public provenance may include only authority, a citation URL when reuse terms explicitly permit it, effective dates, checked time, and an explicit verification status. RERA verification requires an accepted assertion for the exact RERA number, a non-null reviewer, and the official HRERA authority; a scraper run or existing entity is not verification.
- HRERA access is enabled by product decision (written source permission is confirmed) with `HRERA_DATA_ENABLED=true` (the default) and stays fail-closed when an operator turns it off: the flag gates scraper run creation/fetch/write paths, scheduled and manual triggers, public RERA/builder reads, HRERA locality facts/content, and mixed-source market-digest generation. Do not delete cached or persisted locality/property content. Public blog reads must filter known HRERA-derived digests while the flag is off, including cached list/detail/preview results.
- HRERA has no headless listing route. Its project search is CAPTCHA-gated with server-side validation (a posted form returns "Please enter CAPTCHA"), it requires authority, case number, and year together, `view_project/project_list` serves the portal homepage, and there is no JSON or AJAX listing endpoint. Do not write a scraper that assumes a browsable index; `ReraProjectScraper` reports `HRERA_SEARCH_REQUIRES_CAPTCHA` instead of silently returning zero rows. Discovery runs through `rera_portal_scan.ReraPortalIdScanner`, which walks the open `view_project/project_preview_open/{portal_project_id}` pages. That is a bulk operation against a government service, so it is never scheduled: an operator states an id range, each run is capped by `DEFAULT_MAX_IDS`, requests are paced by `DEFAULT_DELAY_SECONDS`, and a run without an `end_id` fails rather than defaulting to an unbounded crawl.
- RERA filing detail is written only from a filing that parsed in full. `RepIFiling.errors` are fatal and block the write; `RepIFiling.notes` record a section that parsed only partly. Collection tables are replaced inside one transaction so a filing is never half-updated. Never fill a field the filing does not state: HRERA publishes no price per square foot, floor count, or coordinates on a filing page, and a passed completion date on a register-live project yields no derived stage rather than an assumed one. `rera_project_people.pan_last4` holds only the last four characters, and `rera_project_bank_accounts.account_number` is never serialized in a public response.
- A RERA filing page states one identifier and it is not the registration number: it carries the portal's pre-registration id (`RERA-GRG-PROJ-1540-2024`), because registration happens after filing. The portal-id scan therefore conflicts on `raw_data ->> 'portal_project_id'` via the partial unique index `idx_rera_projects_portal_project_id`, and records `raw_data.identifier_kind = "temp_project_id"`. Do not key that path on `rera_number`, which would mean inventing a registration number; do not fill `rera_number` from a filing id on any other path. A re-scan refreshes descriptive fields only — `rera_number`, `status`, and `slug` are registration facts or published URL keys and are left untouched, so a re-walk cannot rename a project back to its filing id, revive a revoked project, or move a live URL. **Open gap:** if a future source supplies the real registration number for a project the scan already created, the two rows must be reconciled by hand; nothing merges them automatically, and `identifier_kind` is the marker to find them by.
- Derived values carry their own honesty rules. `project_price_history` points from a filing are `filing` or `launch`; interpolated points are marked `derived` and are written only when both filed prices and both quarters exist and at least one whole quarter sits between them. A developer pillar with no inputs is `None`, and a developer with no pillar data gets no `DeveloperScore` row at all — no data is not a score of zero. `derive_stage` returns nothing rather than assuming a stage. `market_pulse` never reports `negative` from an absent 90-day comparison. `uprera_projects` requires the grid's row count to repeat before reading it, because a streamed multi-megabyte response will otherwise be parsed half-arrived and reported as a complete register.
- A micro-market's statistics are scoped by `rera_projects.micro_market_id`, never by district. Scoping by district made every micro-market in one district report the same project count and the same average rate under a different name, so `/micro-markets/gurugram/sector-76-77` and `/micro-markets/gurugram/golf-course-road` both claimed every project in Gurugram. The link is written by `MicroMarketScraper._link_projects` from the same `derive_locality` that named the market, so a project and its market cannot disagree, and the invariant it maintains is "the link equals the derivation": a project whose address resolves to no locality is set to `NULL` rather than left pointing at a stale market. `_link_projects` reads the market table rather than this run's derived records, so a run that derives nothing — a parser change making every address unreadable, or the pair read hitting its cap — still repairs the links it can instead of silently skipping the pass. Never add a second, weaker scoping rule beside this one.
- A project with no `slug` is not publishable and not watchable. Every project-intelligence read (`/data-hub/projects`, developers, market, watchlist) filters on `slug IS NOT NULL`; the legacy `GET /rera-projects` list does not, and `POST /data-hub/watchlist` applies the same filter, so a watch row always links to a real page. Refusing there is deliberate: a watched row exists to link to the project page, and accepting a slug-less project stores a row the list can only render as `#<id>` with no name, link, or figures. This also means a project id alone is never sufficient to reach a project through any public route.
- `_SCRAPER_MAP` is a dict of dotted strings resolved by import at request time, so no type checker validates it. Any entry added or renamed must keep `test_scraper_trigger_options.py` passing, which imports every entry and constructs it with the filtered operator body; a name pointing at nothing turns an admin trigger into a 500. The map carries the network **source** scrapers, including the HRERA filing refresh. The DB-only derived jobs are absent by convention.
- **The state registers' portal project ids share one numeric namespace, so `raw_data.portal_project_id` belongs to HRERA alone.** That key sits under the partial unique index `idx_rera_projects_portal_project_id`, which HRERA's scanner conflicts on, and the portals number their projects independently in overlapping ranges (HRERA `2779`, Delhi `10143`). A row from another register that wrote `portal_project_id` would be overwritten by an HRERA scan walking the same number, replacing one state's project with another's data. Delhi therefore writes `raw_data.delhi_project_id` plus `raw_data.portal = "delhi_rera"` and never `portal_project_id`; a test stores both registers' rows under one colliding id and asserts both survive. Follow the same pattern for any further register.
- **A district is never fabricated, and a city's identity is its lowercased spelling.** `micro_market` and `market_pulse` both use the filed district as the city, and the registers spell one district inconsistently (`Gurugram` in one filing, `GURUGRAM` in the next), so every write and lookup that means "which place is this" goes through `utils.canonical_city`. The two unique constraints that key on the city (`uq_micro_markets_city_slug`, `uq_market_pulse_snapshots_city_day`) are case-sensitive while the read side matches case-insensitively, so without one canonical spelling one place occupies two rows and two public pages report different numbers for it. A filing whose District label is missing falls back to the **state** — `Haryana`, `Uttar Pradesh`, `Delhi` — never to a district it does not name, because a wrong district is invisible while a state in a district column is visibly wrong. Migration `20261024020000_micro_market_city_lowercase.sql` deduplicates and lowercases existing rows, and must be applied before the next micro-market run on any database that already holds them.

  A canonical city keeps the **spaces** its register filed, and a URL segment cannot carry a space, so the public path joins the words with hyphens (`South West Delhi` → `/micro-markets/south-west-delhi/...`). The web-ui builds that segment with `citySlug` and gates the route with `validSlug`, which rejects a space; the API's `_city_matches` accepts **either** spelling so the site's own link and a hand-typed address both resolve. Ten of Delhi's eleven districts are multi-word, so a space-form link would have 404'd the majority of the Delhi surface while the API answered 200.

## Known Anti-Patterns To Avoid
- Repeating auth, DB session bootstrapping, or validation logic separately in REST, MCP, and AI-agent flows when the same business action already exists in a shared service.
- Mutating ORM state directly inside endpoint or tool wrappers when an equivalent service abstraction exists or should be added.
- Introducing new public runtime surfaces without updating `AGENTS.md`, this contract, and `docs/repo-contract.json`.
